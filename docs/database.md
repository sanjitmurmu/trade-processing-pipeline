# Database Design

## Trade Processing Pipeline

This document is the detailed reference for the database schema used by the Trade Processing Pipeline. It distinguishes the schema represented in the current implementation from tables and columns planned for future milestones.

The entity classes and current application code are authoritative. If a schema example in this document differs from the actual entity mapping or a database migration, update this document to match the implementation.

------------------------------------------------------------------------

# 1. Database Overview

The application currently uses PostgreSQL for trade persistence and the Transactional Outbox.

| Database object     | Purpose                                  | Status                                                                 |
|---------------------|------------------------------------------|------------------------------------------------------------------------|
| `trade`             | Stores processed trade data              | Implemented                                                            |
| `outbox_event`      | Stores downstream events to be published | Implemented                                                            |
| `reference_data`    | Stores symbol-level enrichment data      | Defined in the architecture; verify current persistence implementation |
| `processed_events`  | Supports downstream event idempotency    | Planned                                                                |
| `fee_configuration` | Stores configurable fee rates            | Proposed future design                                                 |

Redis is used separately as a cache for reference data. The Redis cache is not a substitute for the PostgreSQL schema.

# 2. `trade` Table

## 2.1 Purpose

The `trade` table stores the trade after it has been consumed, enriched with reference data, and persisted by the Trade Processor.

The current entity includes the following fields.

| Column          | Type / mapping                      | Constraints and notes                                                 |
|-----------------|-------------------------------------|-----------------------------------------------------------------------|
| `id`            | `BIGINT`-style generated identifier | Primary key; generated by the database                                |
| `trade_id`      | String / `VARCHAR`                  | Required and unique; business identifier used for duplicate detection |
| `symbol`        | String / `VARCHAR`                  | Required                                                              |
| `side`          | Enum stored as string               | Required                                                              |
| `quantity`      | Integer                             | Required                                                              |
| `price`         | `NUMERIC(19,4)`                     | Required                                                              |
| `exchange`      | String / `VARCHAR`                  | Required                                                              |
| `currency`      | String / `VARCHAR`                  | Required                                                              |
| `sector`        | String / `VARCHAR`                  | Required                                                              |
| `brokerage_fee` | `NUMERIC(19,4)`                     | Present in the current entity                                         |
| `tax`           | `NUMERIC(19,4)`                     | Present in the current entity                                         |
| `status`        | Enum stored as string               | Required                                                              |
| `created_at`    | Timestamp                           | Set when the entity is first persisted                                |
| `updated_at`    | Timestamp                           | Set on insert and updated on entity update                            |

The exact lengths for string columns should be taken from the current entity annotations or the generated database schema. They are intentionally not guessed here.

## 2.2 Logical schema

``` text
trade
--------------------------------
id                  PRIMARY KEY
trade_id            NOT NULL, UNIQUE
symbol              NOT NULL
side                NOT NULL
quantity            NOT NULL
price               NUMERIC(19,4) NOT NULL
exchange            NOT NULL
currency            NOT NULL
sector              NOT NULL
brokerage_fee       NUMERIC(19,4)
tax                 NUMERIC(19,4)
status              NOT NULL
created_at
updated_at
```

## 2.3 Idempotency

The consumer checks whether `trade_id` already exists before processing a new event. The unique constraint on `trade_id` is the database-level integrity safeguard.

These mechanisms have different roles:

- Application lookup: avoids repeated processing in the normal case.
- Unique constraint: prevents duplicate trade rows even if concurrent processing bypasses the initial lookup.

If concurrent duplicate processing is introduced, the application should handle a unique-constraint violation deliberately.

# 3. `outbox_event` Table

## 3.1 Purpose

The Outbox table stores an event in the same database transaction as the trade. A separate scheduled publisher later sends the stored payload to Kafka.

This avoids committing a trade without also recording the event that must eventually be published.

## 3.2 Current fields

| Column         | Type / mapping                      | Constraints and notes                                      |
|----------------|-------------------------------------|------------------------------------------------------------|
| `id`           | Generated `BIGINT`-style identifier | Primary key                                                |
| `event_type`   | String                              | Required; for example, `TRADE_CREATED`                     |
| `aggregate_id` | String                              | Required; current code uses the trade identifier           |
| `topic`        | String                              | Required; current configuration uses `trade-notifications` |
| `payload`      | `TEXT`                              | Required; serialized event payload                         |
| `status`       | Enum stored as string               | Required                                                   |
| `created_at`   | Timestamp                           | Set by `@PrePersist`                                       |
| `published_at` | Timestamp                           | Set after successful publication                           |

## 3.3 Logical schema

``` text
outbox_event
--------------------------------
id                  PRIMARY KEY
event_type          NOT NULL
aggregate_id        NOT NULL
topic               NOT NULL
payload             TEXT NOT NULL
status              NOT NULL
created_at          NOT NULL
published_at        NULL until publication succeeds
```

The current enum values are:

``` text
PENDING
PUBLISHED
```

Older design notes used `outbox_events` and `NEW`/`SENT`. Those are historical names; the current implementation uses the singular table name `outbox_event` and statuses `PENDING`/`PUBLISHED`.

## 3.4 Publication lifecycle

``` text
Trade + Outbox Event
        |
        v
One PostgreSQL transaction
        |
        v
Outbox status = PENDING
        |
        v
OutboxPublisherService sends payload to Kafka
        |
     +--+--+
     |     |
  Failure Success
     |     |
     v     v
 PENDING  PUBLISHED
           published_at set
```

The publisher waits for the Kafka send result before marking the event `PUBLISHED`. If the send fails, the event remains `PENDING` for a later scheduled attempt.

A crash after Kafka accepts the event but before the status update can cause duplicate publication. This is an at-least-once design.

# 4. Transaction Boundary

`TradePersistenceService.persistTradeAndEvent()` saves both records inside one `@Transactional` method.

``` text
BEGIN TRANSACTION
    |
    +---- INSERT trade
    |
    +---- INSERT outbox_event
    |
    v
COMMIT
```

If either write fails, both writes roll back.

Kafka publication is deliberately outside this transaction. PostgreSQL and Kafka do not share this local database transaction; the Outbox Publisher bridges the two systems through retries.

# 5. Reference Data Persistence

The architecture defines a reference-data model with one record per symbol.

## 5.1 Proposed logical schema

``` text
reference_data
--------------------------------
symbol              PRIMARY KEY
exchange
currency
sector
```

Example:

| symbol | exchange | currency | sector |
|--------|----------|----------|--------|
| AAPL   | NASDAQ   | USD      | TECH   |
| MSFT   | NASDAQ   | USD      | TECH   |

The Reference Data API response currently includes:

``` json
{
  "symbol": "AAPL",
  "exchange": "NASDAQ",
  "currency": "USD",
  "sector": "TECH"
}
```

**Status:** the response contract is established, but the current database persistence implementation must be checked in the `reference-data-service` source before this table is described as implemented. An API response does not, by itself, prove that the service uses this PostgreSQL table.

Redis cache entries use the cache name `referenceData`, with example key:

``` text
referenceData::AAPL
```

The cache is an optimization; the underlying reference-data source and persistence design should be documented separately.

# 6. Downstream Idempotency — Planned

The original architecture proposes a `processed_events` table so downstream consumers can avoid repeating side effects when Kafka redelivers an event.

## 6.1 Proposed logical schema

``` text
processed_events
--------------------------------
event_id            PRIMARY KEY
processed_at
```

Potential use cases include Notification Service, Audit Service, and Analytics Service consumers.

**Status:** planned. Do not create or document this table as implemented until the downstream consumer and its persistence are added.

Before implementation, define:

- A stable event identifier.
- Whether the record is written in the same transaction as downstream database changes.
- How retries and failures are handled.
- How notification side effects are protected against duplicate delivery.

# 7. Fee Calculation — Planned Schema Changes

The current `trade` entity already contains `brokerage_fee` and `tax`. Fee calculation itself has not yet been implemented.

The planned calculation model is:

``` text
tradeValue       = price × quantity
brokerageFee     = tradeValue × brokerageRate
tax              = tradeValue × taxRate
regulatoryFee    = tradeValue × regulatoryRate
totalFees        = brokerageFee + tax + regulatoryFee
```

## 7.1 Potential future trade columns

| Column           | Proposed type   | Status          |
|------------------|-----------------|-----------------|
| `brokerage_fee`  | `NUMERIC(19,4)` | Already present |
| `tax`            | `NUMERIC(19,4)` | Already present |
| `regulatory_fee` | `NUMERIC(19,4)` | Planned         |
| `total_fees`     | `NUMERIC(19,4)` | Planned         |

The final schema must be confirmed when fee calculation is implemented. Precision, scale, rounding rules, and whether `total_fees` is stored or derived are design decisions still to be made.

## 7.2 Potential `fee_configuration` table

A configurable rate model is preferable to scattering rate constants throughout business logic. One possible future design is:

``` text
fee_configuration
--------------------------------
id
fee_type
rate
active
effective_from
effective_to
```

This is a proposal, not an implemented schema. Before building it, decide whether rates vary by exchange, instrument, trade side, customer, or effective date, and define the uniqueness and lookup rules accordingly.

# 8. Relationships and Integrity

The current design has a logical relationship between a trade and its Outbox Event through the trade identifier:

``` text
trade.trade_id  <---- logical association ---->  outbox_event.aggregate_id
```

The current implementation does not require a declared JPA foreign-key relationship between these entities. Their atomic persistence is provided by the shared transaction in `TradePersistenceService`.

Do not add a foreign key, entity relationship, or cascade rule to the documentation unless it exists in the current schema.

------------------------------------------------------------------------

# 9. Indexes

## 9.1 Confirmed integrity constraints

- Primary keys identify rows in `trade` and `outbox_event`.
- `trade.trade_id` is unique.

## 9.2 Indexes to evaluate

The Outbox Publisher queries by status:

``` text
findByStatus(PENDING)
```

As the number of Outbox Events grows, evaluate an index on `outbox_event.status`. Add it only after reviewing the actual query plan and expected workload.

Other indexes should be driven by observed query patterns rather than added speculatively.

------------------------------------------------------------------------

# 10. Timestamp and Enum Conventions

## Timestamps

The current trade entity sets `created_at` and `updated_at` during persistence and updates `updated_at` on entity update. The Outbox Event sets `created_at` before insertion and records `published_at` after a successful Kafka send.

Confirm the actual database timestamp type and timezone behavior against the entity mappings and application configuration.

## Enums

The trade side, trade status, and Outbox status are stored as strings in the current design.

The current Outbox status values are:

``` text
PENDING
PUBLISHED
```

Use the exact enum constants from source when documenting trade-side and trade-status values.

# 12. Schema Change Workflow

When a database-related feature is implemented:

1.  Update the entity mapping.
2.  Decide how the schema is created or migrated in the project.
3.  Update this document to reflect the resulting schema, not only the proposed design.
4.  Verify column types, nullability, precision, unique constraints, and indexes.
5.  Run the relevant application/database tests.
6.  Update `LLD.md` if entity or repository responsibilities change.
7.  Update `api-contracts.md` and `sequence-diagrams.md` if the persisted or published event contract changes.
8.  Move the capability from Planned to Implemented only after it exists in code.
